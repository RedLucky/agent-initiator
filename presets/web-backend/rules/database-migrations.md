# Database Migrations

- Every schema change is a migration in version control, generated by the project's tool (Prisma, TypeORM, Alembic, Django, goose, …).
- **Never edit or delete an applied migration**; write a new one.
- **Backward compatible (expand → migrate → contract)** — old and new app versions must both work during deploy:
  1. Expand: add new nullable columns/tables; write to both old and new.
  2. Migrate: backfill data in batches.
  3. Contract: remove old columns only in a later release.
- No destructive change (drop/rename column or table, type narrowing) in the same release as the code that stops using it.
- Large tables: create indexes concurrently/online, backfill in batches, avoid long locks.
- Every migration is reversible (down migration) or documents why not.
- Test migrations against a copy of realistic schema/data; never run them on shared or production databases without explicit approval.
- Seeds contain synthetic data only.
